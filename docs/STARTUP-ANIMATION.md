# Pocket Classic 开场动画研究与设计

研究日期：2026-11-08。依据 Android 0.7.2 源码、现有三维模型与品牌设计语言。

最新状态：**Android 0.8.1 已按新版五视图模型整合「转轮序章」**，实现「两圈银环 → 同尺寸真实转轮 → 缩放显示整个机器」，保留最后 0.8 秒的亮屏停留。当前设计、集成及验证见 [转轮序章](WHEEL-OPENING.md)。此前的 [产品展示运镜调研](PRODUCT-MOTION-RESEARCH.md) 与本文下方方案保留为探索记录。

以下为此前概念预览与集成方案的历史研究，包含已放弃的三处环绕运镜，不代表当前开场。

## 推荐结论

采用 **「微距掠光」：现有 Three.js 模型实时演出 + Android 原生启动屏衔接**。

从约 65° 大侧角的整机轮廓与倒影开始，相机沿弧线下移，大幅绕到左侧约 62° 推近转轮；接着沿机身向上移动，绕到 LCD 右侧约 55°、上方约 48° 观察屏框与亮屏过程；亮屏后稳定停留 0.8 秒，再连续后拉、转正，进入真实菜单或恢复播放页。机身旋转固定为零，镜头上方向保持世界竖直，取消额外的画面滚转；环绕与俯仰角度维持原设计。全程保留同一模型、同一画面与连续灯光，最后一帧直接成为可操作的播放器。

保留品牌已有的珍珠白、铂银、淡冰蓝，深色环境使用深蓝灰背景和银色边缘光。高级感主要由构图、光线、细节尺度与缓动节奏形成。

## 已确认的项目条件

- 安卓是 Kotlin / Compose 容器中的本地 WebView，实际播放器界面由 Three.js 0.182.0 绘制；播放由 Media3 服务负责。
- `web-model/front-view.mjs` 已有机身、摄影棚灯、柔和倒影、体感与持续绘制循环，可直接复用场景。
- 当前实际播放器使用正交相机；研究预览使用透视相机，展示更明显的微距运镜。正式接入优先验证正交相机的缩放和构图移动；若选透视运镜，需在终点匹配当前机身尺寸与位置，单独验证衔接。
- LCD 在当前高质量模式下是独立合成的高分辨率画布，逐帧投影到机身位置。机身缩放、旋转与屏幕转场必须同步，避免屏幕漂移或清晰度突然变化。
- `NativePlayerHost.kt` 的 `ready` 表示桥接与状态同步就绪，不能代表三维首帧完成。`three-ready` 类也在首个 `requestAnimationFrame` 之前添加，不能直接当成显示成功信号。
- 当前已有系统与应用内的减少动态效果设置，应覆盖新开场。
- 安卓主题尚未专门配置 AndroidX 启动屏；WebView 默认背景和主题背景需要统一，尤其是深色模式。
- `NativeContract.kt` 校验原生桥接方法白名单。新增视觉就绪信号需要同步更新两侧协议与契约验证。

## 三个设计方向

| 方向 | 建议时长 | 画面顺序 | 适合的感觉 | 主要取舍 |
| --- | --- | --- | --- | --- |
| **微距掠光，推荐** | **5 秒** | 斜侧缓推 → 推近转轮 → 上移到 LCD → 亮屏停留 → 后拉转正 | 机身直立、一镜到底、产品摄影 | 轨迹速度、构图连续性、相机终点和 LCD 对齐要求最高 |
| 悬浮归位 | 3.6 秒 | 约 25–50° 侧前方悬浮 → 缓慢转正 → 稳定落位 → 倒影和菜单显现 | 三维展示、空间感更强 | 运镜更明显，需要更克制的速度和姿态 |
| 转轮序章 | 3.4 秒 | 两道细银环亮起 → 向转轮位置收束 → 金属机身显现 → 屏幕亮起 | 品牌符号、干净、识别性强 | 二维银环和三维转轮需要精确匹配 |

预览的三种方案使用仓库真实机身几何、金属材质、环境贴图与地面倒影；菜单与声纹为演示内容。预览只演示动画，不连接账号、不控制播放。独立预览里的英文副标是氛围实验，正式版本可直接删除，优先保持已有品牌「无言、留白」的方向。

## 推荐方案分镜：微距掠光，5 秒

以下为应用内动画时间轴，不包含系统创建进程、WebView 初始化等不可控等待；用户看到的从点图标到可用的总时间需真机测量。

| 时间 | 画面 | 动效重点 |
| --- | --- | --- |
| 0.00–0.50 秒 | **整机缓推**：以大侧角展示完整机身、厚度与倒影 | 侧角约 65° 缓慢转到 52°，俯角约 24° 转到 16°；机身直立、镜头保持水平 |
| 0.50–1.55 秒 | **推近转轮**：沿大弧线下移、靠近机身下半部 | 连续绕到左侧约 62°；低角度视线随特写距离调整，保持镜头在地面上方 |
| 1.55–2.94 秒 | **沿机身上移**：掠过转轮后，明显抬升并绕到 LCD | 相机连续绕到右侧约 55°、上方约 48°，加强屏框与机身的透视关系 |
| 2.94–3.74 秒 | **LCD 亮屏停留**：保持当前大俯角与焦点 | LCD 已完全亮起，相机稳定停留 0.8 秒；灯光继续柔和流动 |
| 3.74–4.12 秒 | **LCD 滑行**：从大俯角逐渐降低观察角度 | 右侧角由约 55° 转至 36°、俯角由约 48° 转至 34°，准备后拉 |
| 4.12–5.00 秒 | **连续后拉归位**：逐步退回整机、转正 | 相机与焦点平滑收束，字标短暂出现后退出，衔接真实界面 |

整机、转轮、LCD 是同一条运动路径的三个构图重点。所有移动使用位置、速度和加速度连续的五次曲线；LCD 停留前平滑减速，停留后平滑起步。侧向绕行覆盖从左侧约 62° 到右侧约 65°；机身自身不倾斜，仍保留运镜产生的真实透视关系。预览可播放完整路径或拖动时间进度检查；特写期间淡出说明标题，避免挡住材质细节。

精确节奏需要接入实际启动状态后微调。当前以 5 秒进行观感评审，增加的 0.8 秒专用于亮屏停留，原有移动过程保持接近原来的节奏。预览可调至 6 秒进一步放慢。窄屏按主体尺寸调整特写距离，保留转轮和 LCD 的完整边界。每帧沿轨迹采样一次相机姿态，并只绘制一次三维场景；保留倒影与连续灯光，不再使用双视角叠化或切镜。

不默认添加开机音。若后续需要，可提供显式开启的极短声音标记，并遵守静音、音频焦点与现有音乐播放状态。开场期间不主动开始或中断歌曲。

## 实现路线对比

| 路线 | 能力与优势 | 对本项目的成本/局限 | 建议 |
| --- | --- | --- | --- |
| **原生 SplashScreen + Three.js 实时场景** | 复用当前材质和模型；可适配主题、尺寸；最后一帧衔接真实播放器 | 需要启动状态协调、相机演出、首帧预热与真机检查 | **首选** |
| 原生 SplashScreen + CSS / Web Animations | 适合图标淡入、银环收束、界面渐显；新增逻辑较少 | 二维运动易做；精细金属反光、真实微距需要配合现有三维场景 | 用于字标、遮罩、工具栏与转轮序章 |
| Lottie / Rive | 适合设计师制作的二维图形、声纹、品牌符号及状态动画 | 新增运行时与素材维护；三维金属和实时机身的衔接仍需另做 | 二维品牌片有明确素材后再考虑 |
| 预渲染视频，MP4 / WebM | 可制作复杂景深、离线渲染与精细灯光，画质可固定 | 安装包增量、解码、首帧、裁切、多主题与真实机身最后一帧匹配均需处理 | 更适合宣传片或首次介绍 |
| 仅 Android AnimatedVectorDrawable | 小而稳，适合系统启动屏中的图标/声纹动画 | 系统启动屏主要提供图标与单色背景，不能承载完整摄影棚运镜 | 用于最早的品牌占位 |

以上为结合本项目的工程判断，不是实测性能排名。现有 Three.js 不需要为本次动画再引入第二套大型动画引擎；用时间轴函数驱动相机、模型与灯光即可。

## 启动与衔接策略

1. **系统阶段**：配置 AndroidX SplashScreen 与统一的浅/深背景，使用现有银白图标或简短声纹。Android 12 起系统在冷启动、Activity 尚未创建的暖启动显示启动屏，已有 Activity 的热返回不会显示。Google 对系统图标动画建议不超过 1,000 毫秒；本方案 5 秒的产品演出位于应用内容中，不是强行延长系统图标动画。
2. **准备阶段**：后台创建 WebView、生成模型与环境，恢复本地偏好；网络授权状态刷新、封面下载与歌单请求不作为进入界面的前置条件。灯光和材质先配置，再评估 `renderer.compileAsync(scene,camera)` 的预编译收益；它不能替代贴图上传、首帧绘制和真机检查。
3. **视觉就绪阶段**：引入与现有 `ready` 分离的 `visualReady` 信号。至少确认有效视口、状态与 LCD 就位、成功提交首帧，再安排后续帧/原生视觉状态回调进行交接。`onPageFinished()` 本身不保证下一帧已经反映当前 DOM。原生回调也不能单独证明所有异步三维资源都已完成，因此需要场景状态共同判断。
4. **演出阶段**：原生启动屏短淡出，进入同色应用场景。5 秒演出沿一个时间轴连续移动相机，经过整机、转轮、LCD，亮屏停留后再拉回正面；只保留一个 WebGL 渲染器和已有机身实例。开场期间暂时抑制体感和转轮输入，保留跳过操作；禁止把点击跳过传递为播放器点击。
5. **进入阶段**：相机/机身姿态与真实界面匹配，LCD 从开场态转为当前真实状态，释放输入和体感，销毁开场临时内容与事件。
6. **失败阶段**：准备超时退出品牌占位，展示明确可恢复的加载或失败状态。健康场景可跳过演出进入界面；WebGL 初始化失败则显示原生提示，避免无限停在开场。可将 5 秒作为初始准备超时阈值进行真机验证，不将它误当成已经测得的启动时间。

### 生命周期与无障碍

- 正常桌面启动且无可复用界面时，播放标准 5 秒版本。
- 从后台返回、解锁、登录完成返回、通知回到播放器时，直接恢复当前界面。
- 旋转、窗口变化和系统恢复不重复播放；通过实例状态与进程会话状态区分真正新启动与重建。仅检查 `savedInstanceState` 不能涵盖所有入口。
- 提供「完整 / 简短 / 关闭」开场偏好；完整 5 秒，简短约 0.5–0.8 秒。用户已选择更长、更精致且连续经过三处重点的运镜，不能因界面较早就绪便默认砍掉完整演出的核心过程。
- 系统或应用启用减少动态效果时直接显示稳定画面或极短淡入，不做缩放/旋转。两类设置任一开启都生效。
- 开场开始即可跳过；后台化暂停演出，返回时直接收束到播放器。对触屏、读屏和键盘分别提供有效的跳过操作。
- 深浅主题启动前就确定，减少默认浅底与深色播放器之间的突变。机身颜色与环境主题继续保持各自独立。

## 性能与验收

以下是实施时的验收目标，尚未进行本轮安卓真机测量：

- 目标机型在 60 Hz 下以 16.7 ms 为帧预算；低性能设备可接受稳定的 30 fps，依据实测降低像素比、反射开销和运镜复杂度。
- 使用现有分辨率预算；不新建额外 WebGL 上下文，不增加全屏实时模糊、景深后处理或大量粒子。
- 预编译应覆盖开场实际使用的材质、灯光、倒影及最终界面，检查切到新材质状态时是否仍会卡顿。
- 微距应确认材质颗粒、倒角、文字贴图不会因为近距离放大暴露锯齿；这是实时三维与离线视频之间的实际质量边界。
- 安卓全流程测量「点击图标→首个品牌画面」「→演出开始」「→可操作播放器」，区分系统准备时间与 5 秒动画本身。
- 验证银/黑机身、浅/深环境、横/竖屏、首次/已登录/无网、已有后台音乐、减少动态、跳过、Activity 重建与通知返回。
- LCD 与机身全程对齐，末帧亮度与大小连续；动画后转轮、长按定位、体感和工具栏正常，屏幕不被残留遮罩挡住。
- 记录丢帧、显存变化与连续多次打开后的资源情况。历史 README 的短时帧率不能证明新开场的性能。
